## 2. Findings — next batch

### R0-1 · §4's "`make check` runs `install-check` as a step" is false
The conclusion (six CI jobs, not seven) is right; the stated mechanism is not.
`check: lint types test gates` plus `uv run spanweave-live --version` — and the
`Makefile` says so in as many words: *"Deliberately not a prerequisite of
`check`; CI runs both."* CI runs them as **two steps of the `check` job**
(step 5 `make check`, step 6 `make install-check`), which is why the job count
is 4 × `check` + 2 × `conformance` = 6. `CHANGELOG.md` describes the Makefile
correctly; only the §4 line is wrong — and it matters because it inverts the
one thing `CLAUDE.md` and the `Makefile` both insist on, that `make check`
cannot catch a packaging break.
*Fix:* rewrite that §4 sentence as "`install-check` is a second **step** of the
`check` job, not a job of its own, so CI shows six jobs".

### R0-2 · nothing holds the import gate to walking the tree
`package_files()` is a walk today, but mutating it to
`return [PACKAGE_ROOT / name for name in ("__init__.py", "cli.py")]` and adding
`spanweave_live/completion.py` with `import time` + `from random import Random`
leaves `pytest` at `24 passed` and `make check` green. The only tripwire,
`test_the_gate_actually_scanned_something`, asserts
`len(gates.package_files()) >= 2` — exactly satisfied by a two-entry list.
*Fix:* make that tripwire compare `package_files()` against an independently
computed set of `*.py` under the package root. While R3 edits `SEAMS`, keep the
allowlist assertion in exact-dict form rather than relaxing it to membership,
or the widening guard proven in §0(1) stops guarding.

### R1-2 · `push`'s `skipped_records` is asserted nowhere
A `Framer.push` returning `skipped_records=0` unconditionally passes the whole
suite (`92 passed`). The only non-zero assertion in the repo is `flush`'s

SPEC §1.5 and standing rule 5 rest on.
*Fix:* one test pushing a chunk whose complete lines include a malformed one,
asserting `result.skipped_records == 1` directly.

### R1-3 · SPEC §3.5's "re-sorted by the library's own order" is unguarded

plain generator passes 92/92. The test written for it is green because of its

that crossing the 9→10 digit boundary is the point.

### R1-4 · SPEC §3.2's "no dedup cache of its own" is untested
A `self._seen: set[bytes]` inside `Framer` that drops already-seen lines passes
92/92 — and makes a diagnostic vanish: the real behaviour is

diags []`, while under the cache it becomes `records 1, diags []` both ways.
Green only because no corpus rendering holds a byte-identical duplicate line
(`sort -u` equals `wc -l` for all 51) and every hand-authored fixture uses
distinct records. This is standing rule 5, not only spec prose.
*Fix:* one two-part test — the same line twice in one push is one record plus
`duplicate_record`; the same line across two pushes is two records and no
diagnostic.

### R2-1 · SPEC §4.1's declared `Router` surface is narrower than the code's

### R2-2 · gate A's interleaving is line-atomic

cross-trace framing state that is never reached. Extra coverage, not a bug —
R1 already tests the remainder within one stream.
*Fix:* chunk the concatenated interleaved stream rather than each arrival, or
add one test that does.

*Fix:* surface an unclaimed count in `counts`, or one sentence in §4.3 naming
`no_trace.version` as the account. A new event code would be a §3 decision, not
a patch.
